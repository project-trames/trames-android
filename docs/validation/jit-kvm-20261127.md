# Matched JIT / KVM CPU boundaries — 2026-11-27

The current JIT approaches KVM on this supported register-only loop, but a
conditional-branch fallback makes the countdown loop about 7.4–7.6 times slower.
Translated SVC boundaries are much cheaper than nested KVM exits. These are
backend microbenchmarks, **not complete Linux syscalls or Android applications**.

## Matched source and method

- Runtime/JIT: `eefc3b2d9efa46899d68248cae1249a2b2add349`.
- KVM source: Linux `9db947eba448b871f31ca06511c46430bfb35387`.
  Its unchanged KVM crate is linked to the same Runtime snapshot as the JIT in
  a temporary workspace. The Linux product's tested Runtime pin is not changed.
- Existing Lima/VZ ARM64 VM, nested KVM, Linux `7.0.0-44-generic`, actual 4096-byte
  host pages. Both lanes run on vCPU 2, alternating lane order each sample.
- Same original guest instruction bytes and Runtime parallel `View` interfaces.
  Assignment begin/finish and timer-expiry yield recovery use existing CPU hooks.
  No guest instruction patching or production instrumentation is added.
- Rust `nightly-2026-10-16`, release, thin LTO, overflow checks, incremental off.
  Both transports and all four final workloads use binary SHA-256
  `854f9f7bff475de0080ebd1af76a3a6e697cda686a7ce4c736d5c53e14dd1147`.
- Each workload/transport has one complete warm-up plus five measured samples
  per lane. The table is the median of per-sample normalized times: 96 total
  executions, 80 measured. Startup, memory setup and compilation are excluded.

## Results

Integer times are milliseconds per **one million actual ADD operations**;
SVC times are per backend exit and simulated return. Lower is better.

| Workload | JIT paired with SMCCC | KVM SMCCC | JIT paired with MMIO | KVM MMIO |
| --- | ---: | ---: | ---: | ---: |
| Register-only ADD / unconditional B loop | 0.215 ms | 0.225 ms | 0.226 ms | 0.238 ms |
| ADD / SUB / conditional CBNZ countdown | 1.703 ms | 0.224 ms | 1.749 ms | 0.238 ms |
| SVC only, reset entry PC | 5.27 ns | 34.25 us | 5.58 ns | 46.35 us |
| Post-SVC branch + ADD + SVC continuation | 7.81 ns | 36.07 us | 7.85 ns | 46.59 us |

The supported loop is in the same performance range; the observed 4–5% JIT
advantage is not a general ranking. KVM takes about 1/7.6 or 1/7.4 of the JIT
countdown time. SMCCC takes about 6502 times the SVC-only boundary time and
4618 times the continuation time; MMIO ratios are 8314 and 5938 respectively.
These large ratios compare only backend boundaries in this nested VM.

The register-only loop repeats 31 `ADD x0,x0,#1` plus an unconditional `B`.
JIT runs 32 exact 1,048,576-instruction slices; KVM runs 32 existing wall-clock
slices. Their total work is different, so each sample is normalized by its
actual validated x0 increase. This is a throughput comparison, not an equal
instruction-count wall-time comparison.

The countdown executes 31 ADDs, `SUB x1,x1,#1`, `CBNZ x1,loop`, then one final
SVC. Each lane performs four repetitions of 262,144 iterations: exactly
32,505,856 ADDs per sample. x0 delta, x1=0 and final PC are checked. CBNZ currently
falls back to the interpreter: each JIT lane records exactly 6,291,456 fallback
instructions across its six samples. The other three workloads record zero
fallback instructions. The final SVC and backend reentry costs are included.

SVC samples perform exactly 20,000 exits each. The host commits a simulated
return value directly into x0, then resumes the guest. The continuation fixture
starts at its original backward branch and validates both ADD and return-value
progress. The warmed native links and continuation cache are exercised; all
per-workload JIT counters remain in the raw records. The guest SVC becomes a
host control return in the JIT, while KVM traps through private EL1 and its
SMCCC/MMIO exit transport.

## Interpretation and limits

The present integer bottleneck is instruction coverage and transitions into the
interpreter. A supported straight-line loop does not predict branch-heavy,
load/store, flags, SIMD, atomics or general application performance. The JIT
Session/terminal integration and real Android app-UID acceptance remain open.

Neither SVC row executes a Linux syscall handler, VFS operation, host read,
blocking wait or JNI call. There is no matched complete getpid/read/write result
in this record. Do not label the nanosecond numbers as complete syscalls or
extrapolate the thousands-fold boundary ratios to applications. Nested KVM and
host scheduling also limit extrapolation to bare-metal Linux/Android devices.

## Evidence and reproduction

[Raw SMCCC](jit-kvm-20261127/smccc.jsonl),
[raw MMIO](jit-kvm-20261127/mmio.jsonl),
[derived medians](jit-kvm-20261127/summary.json), and
[source/build receipt](jit-kvm-20261127/receipt.json) retain all final samples,
warm-ups, counts and artifact fingerprints. Raw arithmetic, sample identities,
complete sample counts and all derived medians were independently checked.

[Benchmark source](jit-kvm-20261127/bench.rs), workspace/package manifests,
lockfile and toolchain are retained without copying Runtime or VM images.
To reproduce, extract the pinned Runtime commit into `comparison/runtime` and
Linux's pinned `crates/trames-kvm` into `comparison/crates/trames-kvm` using
`git archive`. Place the saved workspace manifest at `comparison/Cargo.toml`,
package manifest at `comparison/bench/Cargo.toml`, benchmark at
`comparison/bench/src/main.rs`, and the saved lock/toolchain at workspace root.
On an ARM64 Linux host with real KVM and 4 KiB pages:

```sh
CARGO_INCREMENTAL=0 cargo build --release --locked --offline -p jit-kvm-compare
TRAMES_KVM_TRANSPORT=smccc taskset -c 2 target/release/jit-kvm-compare
TRAMES_KVM_TRANSPORT=mmio taskset -c 2 target/release/jit-kvm-compare
```

Use an accessible KVM group (the existing VM uses `sg kvm -c ...`) and choose an
available CPU instead of 2 if needed. No Android tools, new VM, rootfs or packages
were installed on the Mac. Only scoped CPU measurements ran; previous product,
Apple, Linux, network and graphics validation remains unchanged.
